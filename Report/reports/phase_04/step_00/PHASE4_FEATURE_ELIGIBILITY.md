# FB69 Phase 4 Feature Eligibility Register

Date: 2026-11-08. Dataset: `data/releases/fb69_player_season_integrated_rs5_v1/player_season_integrated_rs5_v1.parquet` (SHA-256 `4d94ec73…eedd`, 175 columns).

This register turns the accepted rules into eligibility categories for Phase 4.1 and later work. **It is not feature selection.** No statistical screening was done, and no feature was added, removed, imputed or transformed. The final feature set is decided later (P4-D03).

- Column-level register (175 rows): `phase4_feature_eligibility.csv`, generated by `evidence/scripts/p40_eligibility.py` from three release files: `data_dictionary.csv` (roles), `docs/leakage_audit.csv` (leakage class) and `docs/feature_reliability.csv` (reliability).
- Column roles stay defined by `data_dictionary.csv`. Where this register is stricter (for example `m_key_passes`), the stricter rule comes from the accepted Phase 3R documents, cited below.
- Condition ids refer to `PHASE4_CONDITION_REGISTER.md`.

The dictionary flags 108 columns as `candidate_predictor = True` (53 `m_*`, 53 `s_*`, 2 context). This register splits those 108 into 41 candidates, 13 conditional `m_*` features (8 reliability, 5 RD-04), 2 exclusions (`m_key_passes`, `s_key_passes`) and 52 status columns. It adds the 8 club-context columns as conditional, because the leakage audit classifies them REQUIRES RESEARCH DECISION.

## Rules that apply to every column

1. Never use `target_*` columns, `temporal_*` columns, ids or identity columns, or `nationality_profile_present_day` as predictors (P4-A03, P4-A04, P4-A05).
2. Null is not zero. Read the paired `s_*` status before interpreting a null `m_*` value (P4-A07, ISS-25). No imputation or zero-fill. No silent drops.
3. Every `m_*` value is a full-season total or rate. The target is a valuation from a median of 150 days earlier (RD-03). Under Objective A this is not leakage, but it is a construct mismatch, and every relationship must be read with that in mind.
4. `season` and `season_id` are split and grouping keys. Valuation dates come in season-wide batches (ISS-21), so season isn't a free predictor.
5. GK-only metrics are null for outfield rows by design. That null means "not applicable", not "missing".

## 7. Status and missingness indicators (53)

- **52 `s_*` columns** (strings), one per metric, excluding `s_key_passes`. Values across all `s_*` cells: OBSERVED 91,289; MISSING 27,361; UNVERIFIED_POSITION 17,899; OBSERVED_ZERO 5,762; UNSUPPORTED 2,747; OBSERVED_FALLBACK_LEADERBOARD 402; OBSERVED_SOURCE_REVISED 95; CONFLICTING 36. No null `m_*` value has status OBSERVED.
- **`missing_feature_count`**: number of null `m_*` values in the row. Missingness diagnostic only. Mean 17.03 with a usable target vs 42.10 without; GK 34.49 (ISS-27).

The dictionary lists the `s_*` columns as candidate predictors. They describe the source record, not performance. Their mandatory use in Phase 4.1 is to interpret nulls. Any modeling role, such as a missingness indicator, is decided and justified before preprocessing (P4-D01).
